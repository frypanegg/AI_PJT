# 2026 조직건강도 진단 시스템 — 전체 문서

전직원 조직건강도 설문 결과를 부서장이 본인 조직 단위로 열람하고, 조직 운영 인사이트를
얻을 수 있도록 만든 웹 애플리케이션. HR 관리자·경영진용 Admin 화면을 별도로 제공한다.

- **저장소**: `frypanegg/AI_PJT` → `Org_health_diag/`
- **실행 환경**: 로컬 PC 시연 전용 (웹 미배포)
- **총 코드량**: 약 5,000줄
- **구현 버전 2종**: FastAPI + SQLite 웹앱(현행) / Streamlit 프로토타입(검증용, 보존)

---

## 1. 시스템 목적과 사용자

### 1.1 목적

부서장이 본인 담당 조직의 최신 연도 조직건강도 진단 결과를 웹 화면에서 스크롤로 확인하고,
**부서 내부 영역 간 비교** 해석과 챗봇 대화를 통해 조직 운영 방향을 점검하도록 돕는다.

설계 원칙은 하나로 요약된다 — **이 화면이 누군가를 평가하는 데 쓰이지 않는다.**
점수·등급·순위를 넣지 않은 것, 부서 간 비교를 없앤 것, 개인을 특정하려는 질문을 거절하는 것
모두 이 기준에서 내린 결정이다.

### 1.2 사용자 구분

| 사용자 | 진입 경로 | 열람 범위 |
| --- | --- | --- |
| 현업 부서장 (주 사용자) | 조직 LOV + 생년월일 6자리 | **본인 담당 조직 1개만** |

## 4. 데이터

### 4.1 원천 데이터와 연도 확장성

엑셀 워크북의 각 시트가 한 연도에 대응하며, 시트마다
`응답형태 / 법인코드 / 회사명 / 조직명 / 32개 객관식 문항 / C1~C3 주관식` 컬럼을 갖는다.
1행은 컬럼 ID, 2행은 문항 원문, 3행부터 응답 데이터다.

**연도는 코드에 고정되어 있지 않다.** `seed.detect_year_sheets()`가 워크북의 실제 시트
이름에서 4자리 연도를 찾아내고, `analytics.available_years()` / `latest_year()`가 DB에
적재된 연도를 매번 조회한다. 따라서 내년에 2027 시트가 추가된 4개년 파일을 업로드해도
코드 수정 없이 전 화면(섹션 제목·추이 차트·다운로드 파일명)이 자동으로 확장된다.

> 실증 검증: 2027 시트를 추가한 4개년 파일을 관리자 화면에서 실제 업로드해,
> 리포트가 "4개년 변화 분석 (2024–2027)"로 바뀌고 추이 차트 x축이 2027까지 늘어나며
> 다운로드 파일명이 `..._2027_리포트.html`이 되는 것을 확인했다.

### 4.2 SQLite 스키마

| 테이블 | 내용 |
| --- | --- |
| `orgs` | 회사·부서·조직장·인증코드·대상인원 |
| `admins` | 관리자 계정 (SHA-256 해시) |
| `responses` | 객관식 응답 long format (1행 = 1인 1문항), 37,248건 |
| `open_texts` | 주관식 응답, 3,492건 |
| `access_logs` | 로그인·챗봇·다운로드 접근 이력 |
| `chat_messages` | 챗봇 대화 원문 (세션별) |

`responses`는 `(year, org)`, `(year, org, question_id)`, `(year, org, mid)` 인덱스를 갖는다.

### 4.3 6개 조직으로 확장

원본에는 조직이 3개뿐이라, `build_extended_dataset.py`로 포스코·포스코이앤씨 각 3개 부서
(총 6개)로 확장했다. 회사당 1개 유형은 다른 회사의 응답 패턴을 ±1단계 jitter(15% 확률)로
변형한 **합성 복제본**이다.

| 조직 유형 | 포스코 | 포스코이앤씨 |
| --- | --- | --- |
| 건강한 조직 | 철강사업실 (원본) | 철강설계실 (복제) |
| 중립 많은 변화기 조직 | 기술기획실 (원본) | 플랜트설계실 (복제) |
| 개선 신호 조직 | 경영혁신실 (복제) | 건설전략실 (원본) |

### 4.4 중분류별 편차 주입

원본은 조직마다 단일 성향으로 생성되어 있어, 한 조직 안에서는 14개 중분류가 모두 비슷한
수치였다. 그 결과 부서 내부 비교 문구가 대부분 "비슷한 수준입니다"로 나와 시연이 단조로웠다.

`inject_category_variance.py`가 조직×중분류 조합마다 고정 목표 편차를 부여하고
(직원 몰입 수준 ±13%p, 회사 지원 수준 ±17%p, 조직마다 다르게 셔플), 그만큼 실제 응답값을
치환해 긍정 비중을 이동시킨다. 같은 편차를 전 연도에 동일 적용해 "그 팀의 특성"처럼 보이게 했다.

| 지표 | 주입 전 | 주입 후 |
| --- | --- | --- |
| "비슷한 수준" 문구 비율 (중분류 84개 기준) | 64% | **18%** |
| 뚜렷한 차이(8%p 이상) 비율 | — | 57% |

편차는 대분류 안에서 대체로 상쇄되도록 설계해, 조직 전체 평균과 Admin 화면의 부서 간 비교
결과는 거의 변하지 않는다.

### 4.5 응답 척도 변환

5점 척도를 3분류로 집계한다.

| 원 응답 | 분류 |
| --- | --- |
| 전적으로 동의(공감)함 / 동의(공감)함 | **긍정** |
| 어느 쪽도 아님 | **중립** |
| 동의(공감)하지 않음 / 전혀 동의(공감)하지 않음 | **부정** |

### 4.6 문항 계층 구조

```
32개 객관식 문항  →  14개 중분류  →  2개 대분류
```

| 대분류 | 중분류 |
| --- | --- |
| 직원 몰입 수준 | 자발적 몰입, 방향성 제시, 리더에 대한 신뢰, 존경과 인정 |
| 회사 지원 수준 | 급여 및 복리후생, 개발기회, 실행환경 조성, 권한/임파워먼트, 협업, 업무/구조/프로세스, 교육훈련, 가용자원, 성과관리, DEIB |

문항ID→중분류 매핑은 원 기획 문서에 명시되어 있지 않아, 문항 원문을 근거로 이 프로젝트에서
구성했다 (`catalog.QUESTION_TO_MID`).

### 4.7 주관식 문항

| ID | 내용 | 처리 |
| --- | --- | --- |
| C1 | 긍정적 변화 / 자랑할 만한 조직문화 | 원문 미노출, 반복 경향 Top3만 |
| C2 | 개선이 필요한 문화·제도·정책 | 동일 |
| C3 | 일하는 방식 측면 개선점 | 동일 |

## 5. 핵심 분석 로직 — 부서 내부 비교

### 5.1 비교 기준의 변경

프로젝트 중반, HR 부서로부터 **"부서 간 비교를 지양해야 한다"**는 지침을 전달받았다.
초기 구현은 모든 해석을 전사 평균과 비교했는데("전사 평균 대비 +12.5%p 높습니다"),
이는 부서장이 자기 부서의 상대 위치를 역산할 수 있어 사실상 부서 간 비교로 읽혔다.

문구만 바꾸는 대신 **비교 대상 산출 로직 자체를 다시 설계**했다.

| | Before | After |
| --- | --- | --- |
| 비교 대상 | 전사 평균 | 우리 부서 내부의 다른 항목 |
| 예시 문구 | "전사 평균 대비 +12.5%p 높습니다" | "대분류(회사 지원 수준) 내 다른 영역 평균 대비 -14.9%p 낮습니다" |

### 5.2 비교 대상 산출과 3단 폴백

| 대상 | 1순위 | 폴백 |
| --- | --- | --- |
| 중분류 | 같은 **대분류** 안의 다른 중분류 평균 | — |
| 문항 | 같은 **중분류** 안의 다른 문항 평균 | 중분류에 문항이 1개뿐이면(예: 리더에 대한 신뢰) 같은 대분류 안의 다른 문항 평균 |
| 공통 | | 비교 대상이 아예 없으면 비교 없이 분포만 서술 |

```python
diff = 항목 긍정 비중 - 비교 대상 평균 긍정 비중

diff >= +3.0%p  →  "높은 편"            (긍정 해석 카드)
diff <= -3.0%p  →  "관찰이 필요"        (부정 해석 카드)
그 외            →  "비슷한 수준"        (중립 해석 카드)
```

임계값은 `analytics.DIFF_THRESHOLD = 3.0`. 절대 점수·등급은 산출하지 않는다.
이 로직은 리포트 카드/카테고리/문항 해석과 챗봇 답변에 동일하게 적용된다.

**전사 평균은 Admin 화면에만 남겼다** (§10.1).

### 6.1 부서장 리포트 (`/report`)

바로가기 클릭 시 즉시 점프가 아니라 부드러운 스크롤로 이동한다.

| 섹션 | 내용 |
| --- | --- |
| **1. 진단 요약** | 응답 인원·응답률·전체 긍정 비중, 긍정/부정 Top3 영역 카드, 주관식 Top3, AI Executive Summary |
| **2. 카테고리별 결과** | 14개 영역을 **대분류 기준 좌우 분할로 동시 표시**. 왼쪽 회사 지원 수준(9개), 오른쪽 직원 몰입 수준(5개) |
| **3. 32개 문항별 근거** | **문항 원문을 제목으로 크게** 표시, 문항ID·중분류는 작은 메타 정보. 중분류 필터 + 정렬 기준(긍정/부정 높은 순) |
| **4. N개년 변화 분석** | 긍정/중립/부정을 **각각 독립 스케일의 3개 차트**로 분리. 개선 상위 5개 / 관찰 필요 하위 5개. 중분류 선택 시 해당 영역 추이 |
| **5. AI 조직 운영 인사이트** | 관찰 신호, 30일 대화 주제, 구성원 질문 예시, **조직운영 챗봇**, 리포트 다운로드 |

### 6.2 비율 막대 설계

리포트 전반에서 쓰는 핵심 시각 요소로, 세 번의 수정을 거쳤다.

| 문제 | 원인 | 해결 |
| --- | --- | --- |
| 막대 시작 위치가 문항마다 달랐다 | 문항 원문을 차트 y축 라벨로 써서 글자 길이만큼 막대가 밀림 | y축 라벨을 없애고 문항을 HTML 제목으로 분리 → 32개 막대 폭이 전부 동일(실측 952px) |
| 좁은 구간의 수치가 사라졌다 | 스택 막대에서 글자가 안 들어가면 라이브러리가 라벨을 통째로 감춤 | 11% 미만 구간은 막대 오른쪽 **고정폭 칸**에 표시. 웹앱은 렌더링 후 실제 폭을 재서 자동 이동 |
| 막대가 카드 밖으로 밀려났다 | flexbox 기본값(`min-width:auto`)이 내부 텍스트보다 좁아지는 것을 막음 | `min-width:0` + `overflow:hidden` |

설명 문단도 막대와 같은 오른쪽 경계에서 줄바꿈되도록 폭을 맞췄고(`calc(100% - 114px)`),
한글이 음절 단위로 끊기지 않도록 `word-break: keep-all`을 전역 적용했다.

### 6.3 관리자 화면 (`/admin`)

| 섹션 | 내용 |
| --- | --- |
| **1. Raw Data 업로드** | 설문 원본 엑셀 업로드로 전체 분석 데이터 교체, 기본 더미 데이터로 되돌리기 |
| **2. 부서별 결과 비교** | 전사 평균 대비 ±3%p 기준으로 우수 / 관심 필요 / 평균 분류. 표 + 막대차트(전사 평균 기준선) |
| **3. 부서별 변화 추이** | 부서별 긍정 비중 라인차트 |
| **4. 부서장별 접근 이력** | 회사·부서·조직장명 · 로그인 / 챗봇 / 다운로드 이력 (횟수 + 최근 시각) |

업로드 파일은 적재 전 연도 시트 존재 여부를 검사하고, 실패 시 예외를 잡아 기존 데이터를
유지한다. 적재는 트랜잭션으로 처리해 부분 적용이 남지 않는다.

## 7. 인증과 접근 로그

### 7.1 부서장 인증

조직 LOV 선택 + 생년월일 6자리. URL 파라미터(`?org=ss`)로 조직을 사전 선택한 개인화 링크를
메일로 배포하는 시나리오를 지원한다. 인증코드는 화면에 노출하지 않고 `DEMO_GUIDE.md`로만 전달.

### 7.2 관리자 인증

로그인 화면 우측 상단 **🔐 Admin** 버튼 → 별도 ID/PW. 부서장 인증과 완전히 분리된 경로다.
비밀번호는 SHA-256 해시로 보관한다(데모 수준 — §12 참조).

### 7.3 세션

Starlette `SessionMiddleware`(서명 쿠키)를 사용한다. 서명 키는 `SESSION_SECRET` 환경변수가
없으면 최초 실행 시 생성해 `webapp/.session_secret`에 보관한다(git 제외).

**대화 기록은 세션에 두지 않는다.** 세션 전체가 쿠키에 담기는 구조라 AI 답변 몇 개만 쌓여도
브라우저의 쿠키 용량 한계(약 4KB)를 넘어 이후 저장이 조용히 실패했다. 대화는 `chat_messages`
테이블로 옮기고 쿠키에는 짧은 세션 토큰만 남긴다.

### 7.4 접근 로그

모든 이벤트를 `access_logs` 테이블에 기록한다.

| 이벤트 | 발생 시점 |
| --- | --- |
| `login_success` / `login_failed` | 부서장 로그인 시도 |
| `admin_login_success` / `admin_login_failed` | 관리자 로그인 시도 |
| `logout` | 로그아웃 |
| `chat_message` | 챗봇 질문 전송 |
| `report_download` | 리포트 HTML 다운로드 |
| `raw_data_upload` | Raw Data 교체 |

## 8. 챗봇

### 8.1 라우팅 우선순위

| 순위 | 조건 | 처리 |
| --- | --- | --- |
| 0 | **개인 특정 + 징계 의도 동시 감지** | **응답 거부** — 익명 집계임을 안내하고 원인 관점으로 전환 |
| 1 | 인사말 키워드 | 환영 메시지 |
| 2 | 다음 단계 키워드 (`다음`, `30일`…) | 부정 Top3 영역의 권장 대화 방향 |
| 3 | 요약 키워드 (`요약`, `전체`…) | 전체 비중 + Top3 요약 |
| 4a | 중분류 키워드 + **짧은 조회** | 집계 카드 (로컬, 외부 호출 없음) |
| 4b | 중분류 키워드 + **문장형 후속 질문** | **근거 기반 LLM 답변** — 그 부서의 실제 수치를 컨텍스트로 전달 |
| 5 | 매칭 실패 | Web Advisor 위임 (일반 리더십 질문) |
| 6 | Web Advisor 실패/비활성 | 14개 영역 목록 안내 |

**4a / 4b 구분이 핵심이다.** 초기 구현은 중분류 키워드가 포함되기만 하면 무조건 같은 카드를
반환해, "가용자원이 한정적인데 어떻게 조율할까요?" 같은 후속 질문에도 요약만 반복했다.
지금은 길이와 의문 표현으로 조회와 질문을 구분해, 후속 질문은 데이터를 근거로 실제 답을 한다.

### 8.2 근거 기반 답변 (grounded-skill)

웹검색 없이, 해당 영역의 집계 수치와 해석 문장만 컨텍스트로 넘겨 LLM이 답한다.

**시스템 프롬프트 원칙**: 주어진 데이터에 없는 수치 생성 금지, 개인 지목·평가 금지,
징계/처벌적 관리 권장 금지, 처방 대신 점검 방향 제시, 점수·등급·순위 표현 금지.

### 8.3 Web Advisor (search-skill)

일반 리더십/조직관리 질문을 처리한다.

```
질문 → Tavily 웹검색(상위 4건) → OpenAI로 종합 → 답변 + 출처 링크
```

**개인정보 보호**: 외부로 전송되는 것은 사용자가 입력한 질문 문장뿐이며, 조직의 진단
데이터는 전달되지 않는다.

**Fail-safe**: API 키 미설정이거나 호출 실패 시 항상 조용히 `None`을 반환하고 예외를 밖으로
던지지 않는다. 상위 로직이 자동으로 대체하므로 키 없이도 앱은 정상 동작한다.

## 9. 리포트 내보내기

리포트 요약과 챗봇 대화를 인라인 CSS가 포함된 단일 HTML 파일로 조립해 다운로드한다.

**포함 항목**: 조직명/생성 시각, 전체 응답 비중, 긍정/부정 Top3, AI Executive Summary,
**챗봇 대화 요약**, 전체 대화 원문(접이식).

대화 기록은 원문을 그대로 싣지 않고 **별도 LLM 호출(summary-skill)이 요점을 불릿으로 정리**해
앞에 배치하고, 원문은 `<details>`로 접어 함께 담는다. API 키가 없으면 요약 없이 원문만 싣는다.

사내 메일 서버 연동이 없어 **발송이 아닌 다운로드까지만** 지원한다.
사용자 입력값은 `html.escape()` 처리한다.

## 10. Guardrail (06_guardrails.md 대응)

| 원칙 | 구현 | 근거 위치 |
| --- | --- | --- |
| 점수·등급·순위 미제공 | 스키마에 총점/등급 필드 자체가 없음 | 설계 단계 |
| 개인 응답 원문 미노출 | 주관식은 동일 응답 빈도 Top3만 집계 | `top_open_texts` |
| 소수 응답 조직 보호 | `MIN_RESPONDENTS = 10` 미만 시 리포트 차단 | `is_suppressed` |
| 조직장 개인 평가 금지 | 14개 영역 × 긍정/중립/부정 문장을 사전으로 고정 | `MID_INTERPRETATION` |
| 부서장은 본인 조직만 조회 | 인증된 `org_key` 기준으로만 조회 | `require_org` |
| **부서 간 비교 지양** | 부서장 화면의 모든 비교를 부서 내부로 한정 | `peer_avg_for_*` |
| **개인 특정·징계 요청 차단** | 징계 의도 + 특정 의도 동시 감지 시 응답 거부 | `is_punitive_request` |
| 접근 이력 기록 | 로그인·챗봇·다운로드 전부 로깅 | `access_logs` |
| AI 데이터 최소 전달 | 웹검색 경로에는 질문 문장만 전달 | `web_advisor.answer` |

### 10.1 관리자 화면의 의도적 예외

부서장 화면은 부서 간 비교를 전면 배제하지만, **Admin 화면은 HR 관리자·경영진이 부서 간
상태를 비교·점검하는 것이 본래 목적**이므로 전사 평균 대비 우수/관심 필요 구분을 의도적으로
제공한다(점수·등급은 여전히 미제공). 같은 데이터라도 보는 사람에 따라 허용 범위를 다르게
설계한 것이며, 이 때문에 별도 관리자 계정으로만 접근 가능하다.

## 11. 실행 방법

### 11.1 웹앱 (현행)

```bash
cd Org_health_diag/webapp
pip install -r requirements.txt
python seed.py                    # 최초 1회: 엑셀 → SQLite 적재
uvicorn main:app --port 8000
```

접속: `http://localhost:8000`
`seed.py`를 건너뛰어도 앱 기동 시 DB가 비어 있으면 자동 적재한다.

### 11.2 Streamlit 프로토타입 (보존)

```bash
cd Org_health_diag/streamlit_app
pip install -r requirements.txt
streamlit run app.py
```

접속: `http://localhost:8501`. 포트가 달라 웹앱과 동시 구동이 가능하다.

### 11.3 외부 API 활성화 (선택)

`OPENAI_API_KEY`, `TAVILY_API_KEY`를 상위 폴더 `.env`에 두면 자동으로 읽는다.
없으면 근거 기반 답변·웹검색·대화 요약만 비활성되고 나머지는 정상 동작한다.

### 11.4 계정 정보

부서장 6개 조직의 개인화 URL·인증코드와 관리자 계정은 `streamlit_app/DEMO_GUIDE.md` 참조.

## 12. 알려진 제한사항

- **웹 미배포 로컬 데모**이며, 인증은 SSO가 아닌 조직+생년월일 데모 로직이다.
- **비밀번호 해시가 데모 수준**이다. SHA-256 단순 해시를 쓰므로 실서비스에서는
  bcrypt/argon2 + per-user salt로 교체해야 한다.
- **AI 해석 문장(리포트 본문)은 실시간 LLM 호출이 아니다.** 해석 사전 기반 규칙 로직으로
  생성한 예시다. 챗봇의 후속 질문 답변·웹검색·대화 요약만 실제 LLM을 사용한다.
- **응답률의 "대상 인원"은 가정치**다. 더미 데이터에 없는 값이라 임의 지정했고 화면에도
  "가정치"로 표기한다.
- **6개 조직 중 3개는 합성 복제 데이터**이며(§4.3), 중분류별 편차도 인위적으로 주입한
  것이다(§4.4). 실제 설문 결과가 아니다.
- **업로드 데이터는 조직 목록을 바꾸지 않는다.** 부서 구성은 `orgs` 테이블에 시드되어 있어,
  등록되지 않은 조직명이 파일에 있어도 화면에 나타나지 않는다.
- **단일 프로세스 구동 전제**다. SQLite와 로컬 세션 키를 쓰므로 다중 워커 구성 시
  DB 이관과 세션 스토어 분리가 필요하다.
- **리포트 메일 발송 미지원** — HTML 다운로드까지만 제공한다.
- 조직장명은 데모용 가상 인물이다.

## 13. 향후 확장 방향

| 항목 | 현재 | 전환 방향 |
| --- | --- | --- |
| 인증 | 조직+생년월일 | 사내 SSO + 권한 매핑 테이블 |

| AI 비용 | 질문마다 API 호출 | 응답 캐싱 + 호출량 상한 |
| 운영 | 단일 프로세스 · SQLite | 다중 워커 + PostgreSQL |
| 리포트 배포 | 수동 다운로드 | 사내 메일 서버 자동 발송 |
| 접근 로그 | 로컬 SQLite | 중앙 감사 로그 시스템 |
